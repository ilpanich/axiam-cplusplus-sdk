1// axiam WebAuthn / passkeys — CONTRACT.md §24.
2//
3// WHAT IS HERE, AND WHAT DELIBERATELY IS NOT.
4//
5// The six relying-party wire operations, plus §24.6a's JSON bridge. What is not
6// here is §24.6b's linked-API ceremony helper: a C++ program has no
7// authenticator on the targets this SDK serves — there is no platform API to
8// link — and §24.6b rule 2 forbids emulating one in software, because a
9// "credential" held in process memory is not a second factor.
10//
11// That is a statement about convenience, not about capability. §24.6a is the
12// seam that makes it so: WebauthnChallenge::request_json() hands out the
13// challenge in the exact JSON form every platform authenticator API takes, and
14// every *_finish takes the platform's response JSON back as a string, byte for
15// byte. An embedded gateway that fronts a browser, a native app talking to a C++
16// service, or a test harness driving a virtual authenticator all use the same
17// two seams.
18//
19// THE SERVER OWNS THE OPTIONS (§24.0). Nothing here defaults a field, validates
20// one, or re-encodes a buffer. The challenge arrives as JSON text and leaves as
21// JSON text; the authenticator's response is spliced into the request body
22// without being parsed into a model and printed back out. A signed buffer that
23// makes a round trip through a JSON model is a signed buffer that can come out
24// different.
