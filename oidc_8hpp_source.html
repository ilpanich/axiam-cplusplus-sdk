1// §12 OIDC relying party, §12.7 logout, §14 device grant, §15 token exchange.
2//
3// WHY THIS FILE EXISTS AT ALL. Contract 1.10 and earlier deferred §12 in the
4// Swift, C and C++ SDKs: these are device- and IoT-oriented, and the
5// browser-redirect relying-party flow has no natural home in any of them.
6// Contract 1.11 (§12.6) reverses that, and the reason is worth keeping next to
7// the code. The persona argument only ever covered two of the thirteen
8// operations —
9// `oidc_begin` and `oidc_exchange`, the pair that genuinely assumes a browser.
10// The other seven are exactly what an embedded consumer wants:
11// `login_client_credentials` is machine-to-machine login, `introspect` and
12// `revoke` are ordinary questions a device asks about its own credentials, and
13// `oidc_refresh` is the grant the §9 single-flight guard was built for.
14// Meanwhile §14 (device grant) exists *because* a device cannot show a browser,
15// and §20 (UMA) already gave this SDK a `/oauth2/token` call — so by 1.10 it was
16// speaking OAuth2 at the token endpoint anyway, without the shared discovery
17// cache and ID-token validation §12 specifies. This removes a divergence rather
18// than adding one.
19//
20// THE FOUR THINGS THIS SURFACE WILL NOT DO FOR YOU:
21//
22// 1. It stores no `state`, `nonce` or `code_verifier` (§12.3 rule 1). They come
23// back out of Client::oidc_begin and the caller hands them to
24// Client::oidc_exchange. There is no implicit cache, and the caller must
25// also remember its own `redirect_uri` — RFC 6749 §4.1.3 requires it
26// replayed byte-identically and AuthorizationRequest deliberately does not
27// carry it (§12.1).
28// 2. It never skips ID-token validation. There is no flag, no "insecure" entry
29// point, and no partial result: §12.4 rule 7 is all-or-nothing, so a token
30// set whose `id_token` fails any check is discarded whole — the access and
31// refresh tokens from the same response never reach the caller.
32// 3. It adopts nothing. Every operation here returns tokens; none of them
33// become this client's own credential. §15.2 rule 5 makes that a MUST NOT
34// for the exchanged token specifically, and this SDK takes the same posture
35// everywhere rather than having two.
36// 4. It does not retry a grant. §16.2 lists `oidc_exchange`, `device_authorize`,
37// `device_login` and `token_exchange` as ineligible, because their
38// credentials are single-use: retrying replays a spent authorization code or
39// device code and turns a blip into a hard `invalid_grant`. Only the
40// read-only calls here — discovery, introspection, a `device_poll` that hit
41// a 5xx — go through §16.
