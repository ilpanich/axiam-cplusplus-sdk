1// §28 MCP Resource-Server Helpers (RFC 9728 + RFC 6750), CONTRACT.md contract
2// 1.48.
3//
4// This is the RESOURCE SERVER's half of the Model Context Protocol
5// authorization handshake: publishing the RFC 9728 protected-resource
6// metadata document that names the authorization server guarding this
7// resource, and building the `WWW-Authenticate` challenge that starts an MCP
8// client's discovery. AXIAM is the authorization server and implements none
9// of this; the *client* half — parsing a challenge, fetching a document,
10// deciding whether to trust the authorization server it names — is
11// deliberately not in this contract version, for the same reason §20.3 stops
12// at parsing a UMA challenge rather than acting on one.
13//
14// §28.0: **no operation here performs network I/O.** All three are pure
15// local computation, like oidc_begin (§12.1) and uma_parse_challenge (§20.5),
16// so §16's retry policy and §9's single-flight refresh do not apply and
17// nothing here touches the SDK client's own session.
18//
19// **Nothing in this file is a source of truth about a token.** The document
20// is a claim a resource server publishes about itself; the challenge is a
21// hint given to a caller that already failed. Whether a request is
22// authorized stays §10.1's and §11's decision, unchanged and unreachable from
23// here — see <axiam/authenticator.hpp> and <axiam/guard.hpp> for where the
24// challenges built here actually get attached to a 401/403.
25//
26// **C++ has no router** (§28.3), so there is no `serve_protected_resource_metadata`
27// function in this SDK: README.md documents the Crow/Pistache adapter that
28// registers the derived path by hand, using `protected_resource_metadata()`
29// and `ProtectedResourceMetadataDocument::to_json()` below.
