1// §20 UMA 2.0 — Protection API and ticket grant.
2//
3// The resource-server side of User-Managed Access: a service that guards
4// resources on someone else's behalf registers them, asks the authorization
5// server what a caller would need, and exchanges the resulting ticket for a
6// Requesting Party Token.
7//
8// WHY THIS SHIPS WHILE §12 DOES NOT. The README defers §12.7, §14 and §15
9// because each needs an OIDC layer this SDK does not have — a discovery cache,
10// ID-token validation, PKCE. §20 needs none of it: UMA carries its OWN
11// discovery document (`/.well-known/uma2-configuration`, §20.1's named wire
12// reference), the Protection API is ordinary bearer-authenticated REST, and the
13// ticket grant returns an opaque RPT with no `id_token` to validate. One GET and
14// one POST. The parallel-stack objection genuinely does not apply here, so the
15// deferral would have been a habit rather than a reason.
16//
17// THE RULE THIS FILE EXISTS TO ENFORCE. A permission ticket is single-use and
18// is NOT retryable. Every other refusal in this SDK can be re-sent after the
19// caller fixes something; this one cannot — the ticket is spent whether or not
20// the exchange succeeded. See Client::uma_exchange_ticket.
